# 🌱 Git 기초 — 커밋·푸시·PR이 뭐야?

> [!tip] 한 줄로
> **커밋** = 내 컴퓨터에 "저장 지점" 찍기
> **푸시** = 그 저장 지점을 인터넷(GitHub)에 올리기
> **PR** = "제 작업 원본에 합쳐도 될까요?" 하고 올리는 검토 요청서

디자이너라면 **Figma의 버전 기록(Version history)** 이랑 거의 똑같다고 생각하면 돼요.

---

## 1. 먼저 알아야 할 두 가지

### Git (깃)
- 파일의 **변경 기록을 관리하는 프로그램**.
- "최종.psd, 최종_진짜.psd, 최종_진짜_마지막.psd" 지옥을 없애주는 도구.
- 언제, 누가, 무엇을 바꿨는지 전부 기록되고 **언제든 예전 상태로 되돌릴 수 있음**.

### GitHub (깃허브)
- Git으로 관리하는 프로젝트를 **인터넷에 올려두는 사이트**. (Git = 도구, GitHub = 그 도구로 만든 걸 보관하는 클라우드)
- 비유: Git = 내 컴퓨터의 Figma 파일 버전 기록 / GitHub = Figma 클라우드
- 지금 너의 `projektory`가 GitHub에 올라가 있는 프로젝트야.

---

## 2. 핵심 용어 (디자이너 비유)

| 용어 | 뜻 | 디자이너 비유 |
|---|---|---|
| **레포지토리** (repository, 줄여서 "레포") | 프로젝트 폴더 + 그 폴더의 모든 변경 기록 | Figma 파일 하나 + 버전 기록 전체 |
| **커밋** (commit) | 지금까지 바꾼 내용을 **메시지를 붙여서 저장 지점으로 기록** | Figma에서 "Save to version history" 누르고 "메인 배너 색상 수정" 이라고 이름 붙이기 |
| **커밋 메시지** | 그 저장 지점에 붙이는 설명 | 버전 이름 |
| **푸시** (push) | 내 컴퓨터에 있는 커밋들을 **GitHub(온라인)에 업로드** | 로컬 파일을 클라우드에 동기화 |
| **풀** (pull) | 반대로 GitHub에 있는 최신 내용을 **내 컴퓨터로 내려받기** | 동료가 수정한 최신 버전 받아오기 |
| **클론** (clone) | GitHub 레포를 **내 컴퓨터에 통째로 복사** | 공유받은 파일 "Duplicate" 하기 |
| **브랜치** (branch) | 원본을 건드리지 않고 **갈라져 나온 작업 라인** | Figma의 브랜치 기능 / "시안 B" 페이지 따로 만들기 |
| **main** (메인 브랜치) | 원본, 공식 버전 | 클라이언트에게 확정된 최종 시안 |
| **PR** (Pull Request, 풀 리퀘스트) | "내 브랜치 작업을 main에 합쳐주세요" 하는 **검토 요청서** | 팀장님께 "시안 검토 부탁드려요" 하고 코멘트 받기 |
| **머지** (merge) | 브랜치 작업을 main에 **합치기** | 시안 B를 확정본에 반영 |
| **diff** (디프) | 바뀐 부분만 비교해서 보여주는 것 | Before / After 비교 |
| **충돌** (conflict) | 두 사람이 같은 곳을 다르게 고쳐서 Git이 어느 걸 쓸지 모르는 상태 | 두 디자이너가 같은 버튼을 다른 색으로 바꿈 |

## 3. 전체 흐름 한눈에

```
 [내 컴퓨터]                              [GitHub (인터넷)]
 파일 수정
   ↓  git add   (이번 저장에 넣을 파일 고르기)
   ↓  git commit (저장 지점 찍기 + 메시지)
   ↓  git push  ─────────────────────────→  내 브랜치에 업로드됨
                                              ↓
                                           PR 만들기 (main에 합쳐도 될까요?)
                                              ↓
                                           검토·코멘트
                                              ↓
                                           머지 → main(원본)에 반영!
```

---

## 4. 이번에 내가(Claude) 한 일을 이 용어로 다시 설명하면

1. 너의 `projektory` **레포**에서 `claude/ai-expert-instagram-strategy-rr7r8o` 라는 **브랜치**(원본 안 건드리는 작업 라인)에서 작업했어.
2. `strategy/AI_GROWTH_PLAN.md` 파일(전략 문서)을 만들고 → **커밋**(저장 지점 찍기)했어. 메시지: "Add AI growth plan…"
3. 그걸 GitHub에 **푸시**(업로드)했어. → 지금 GitHub 사이트에서 그 브랜치를 고르면 파일이 보여.
4. **PR은 아직 안 만들었어.** 그래서 main(원본)에는 아직 안 합쳐진 상태야.

> [!question] 그럼 PR은 언제 만들어?
> main에 합치고 싶을 때! 예를 들어 GitHub Pages(GitHub의 무료 웹사이트 공개 기능)는 보통 main 브랜치 내용으로 사이트를 보여줘. 그래서 **사이트에 실제로 반영하고 싶으면 PR → 머지** 를 해야 해. 말만 하면 PR 만들어줄게.

## 5. 직접 해보는 명령어 (터미널에서)

| 하고 싶은 것 | 명령어 | 설명 |
|---|---|---|
| 상태 보기 | `git status` | 뭐가 바뀌었는지 확인 |
| 저장할 파일 고르기 | `git add 파일이름` (전부면 `git add .`) | "스테이징"(이번 커밋에 넣을 파일 담기) |
| 저장 지점 찍기 | `git commit -m "메시지"` | 커밋 |
| 업로드 | `git push` | 푸시 |
| 최신 내려받기 | `git pull` | 풀 |
| 브랜치 만들기 | `git checkout -b 새브랜치이름` | 작업 라인 새로 만들기 |
| 기록 보기 | `git log --oneline` | 커밋 목록 |

> [!tip] 디자이너 꿀팁
> 명령어가 무서우면 **GitHub Desktop** 앱(버튼으로 하는 Git)이나 **VS Code / Cursor**의 소스 관리 탭을 쓰면 버튼으로 다 돼. 그리고 요즘은 Claude Code 같은 AI 코딩 에이전트에게 "커밋하고 푸시해줘" 라고 말만 해도 돼.

## 6. 좋은 커밋 메시지 쓰는 법
- 무엇을 했는지 **동사로 시작**: "메인 배너 색상 변경", "다크모드 추가"
- 한 커밋 = 한 가지 일 (여러 개 섞지 않기)
- 나중의 내가 읽고 이해할 수 있게
